# Laptop display and AniMe Matrix power research

Research for [Establish reliable screen and lid-light control](https://github.com/teevik/homelab/issues/64), within [Design a distinctive laptop health display](https://github.com/teevik/homelab/issues/62). Investigated 2026-09-30; repository baseline `13103fe5a246dcd6e1d4444bbf4e5080182a3818`. This is a design investigation, not a deployment or hardware test.

## Design implications

A minimal Sway session can host either a custom GUI or a full-screen terminal running a custom TUI, and provide the same output-power control for both. Choosing a terminal aesthetic does not require choosing Linux's raw virtual console. Prefer this shared display layer unless avoiding a compositor is itself a requirement. Sway documents `output <name> power off/on`, preserving windows; `disable/enable` instead removes the output's workspaces. Discover the built-in connector with `swaymsg -t get_outputs`; do not assume its name is `eDP-1`. [Sway output manual](https://github.com/swaywm/sway/blob/master/sway/sway-output.5.scd)

Use one controller that computes the desired state from current Oslo time and explicit overrides. Timers should request reconciliation, not independently issue unconditional on/off commands. The current AniMe implementation also needs controller ownership and an additional defense against firmware/daemon event handlers turning LEDs back on. These are design recommendations inferred from the mechanisms below, not yet implementation choices.

## What the repository establishes

- The host ignores lid-close suspend, enables graphics support and asusd, enables AniMe with medium brightness, disables built-in animations, and asks AniMe to turn off on lid close, battery, and suspend. Keyboard backlight is written to zero at boot. These are configured intentions, not observations of the laptop. [Host configuration](https://github.com/teevik/homelab/blob/13103fe5a246dcd6e1d4444bbf4e5080182a3818/hosts/homelab/configuration.nix)
- `anime-matrix-stats` starts at `multi-user.target`, restarts after failure, and disables the display in `ExecStopPost`. Its Go program explicitly enables the display at startup and then uploads an image roughly every 15 seconds. It does **not** explicitly re-enable the display on every frame. Night mode should stop this producer and prevent its automatic startup/restart from bypassing the night policy. A deliberate `systemctl stop` is not undone by `Restart=on-failure`. [Service](https://github.com/teevik/homelab/blob/13103fe5a246dcd6e1d4444bbf4e5080182a3818/modules/nixos/anime-matrix.nix), [program](https://github.com/teevik/homelab/blob/13103fe5a246dcd6e1d4444bbf4e5080182a3818/packages/anime-matrix-stats/main.go), [systemd restart semantics](https://github.com/systemd/systemd/blob/main/man/systemd.service.xml)
- The baseline pins nixpkgs `5880666…`, which packages asusctl **6.3.7**. The package version matters to the event-handler caveat below. [Lockfile](https://github.com/teevik/homelab/blob/13103fe5a246dcd6e1d4444bbf4e5080182a3818/flake.lock), [pinned package](https://github.com/NixOS/nixpkgs/blob/5880666fd9eb563038431edb35c2d0aa595884e6/pkgs/by-name/as/asusctl/package.nix)

## Screen control and automatic startup

For either visual style, a dedicated session can start through NixOS greetd and Sway. The pinned NixOS modules provide greetd settings and Sway session integration, including importing `SWAYSOCK` into the user service environment. A controller running outside the session must address the correct session/socket; guessing a socket path is fragile. Autologin, session restart, and application restart are distinct concerns: the pinned greetd module changes its restart default when `initial_session` is present. Design their recovery paths explicitly. [Pinned greetd module](https://github.com/NixOS/nixpkgs/blob/5880666fd9eb563038431edb35c2d0aa595884e6/nixos/modules/services/display-managers/greetd.nix), [pinned Sway module](https://github.com/NixOS/nixpkgs/blob/5880666fd9eb563038431edb35c2d0aa595884e6/nixos/modules/programs/wayland/sway.nix)

Sway output power control asks the display stack to turn the output off; a black dashboard or screen-lock background only draws black and does not establish panel/backlight power-off. Keep the compositor and application running while dark. Do not install unconditional wake-on-input behavior: the common swayidle example explicitly runs `power on` on resumed activity, and pending resume commands also run when swayidle terminates. If swayidle is used, its resume path must consult the same night policy. Alerts should update application data only and never call a wake action. [Sway output manual](https://github.com/swaywm/sway/blob/master/sway/sway-output.5.scd), [swayidle manual](https://github.com/swaywm/swayidle/blob/master/swayidle.1.scd)

A raw-console TUI has weaker portable guarantees. `setterm --blank force` is virtual-console-only and can keep the console blank despite keypresses; `--blank poke` unblanks it. Its VESA power-saving controls are separate. Console blanking alone is not proof that this laptop's backlight is off. Linux exposes `bl_power=4` for backlight power-off and `0` for on, but the appropriate backlight device and effective behavior require hardware inspection. A graphical terminal uses the compositor's output control, not these console escape sequences. [util-linux setterm manual](https://github.com/util-linux/util-linux/blob/master/term-utils/setterm.1.adoc), [kernel backlight ABI](https://www.kernel.org/doc/Documentation/ABI/stable/sysfs-class-backlight)

Display power is separate from host suspension. Preserve lid-ignore behavior and ensure the chosen session has no idle-suspend action; do not use `systemctl suspend` as a bedtime operation. logind defines lid handling and `IdleAction` separately. [logind configuration](https://github.com/systemd/systemd/blob/main/man/logind.conf.xml)

## Schedule, overrides, and reconciliation

Accepted policy: darkness from **23:00 inclusive to 08:00 exclusive, Europe/Oslo**, manual bedtime until morning, explicit wake, and no alert-triggered wake. Implementation proposal:

1. A controller serializes state changes for the panel and AniMe producer. It reconciles at boot, session readiness/restart, asusd restart, display reconnect, policy boundary, manual request, and clock correction. A periodic reconciliation can recover missed notifications, but cannot guarantee that no brief flash occurred between checks.
2. Use `OnCalendar=*-*-* 23:00:00 Europe/Oslo` and `OnCalendar=*-*-* 08:00:00 Europe/Oslo` to invoke that same reconciler. Set timer accuracy deliberately; the default coalescing window is a minute. `Persistent=true` catches missed calendar activations, but does not encode current desired state: after downtime both independent unconditional on/off timers could have missed events. Recomputing current policy removes that ordering problem. `OnClockChange` can also request reconciliation. [systemd timer definitions](https://github.com/systemd/systemd/blob/main/man/systemd.timer.xml)
3. Use the IANA zone in both timer expressions and state calculations. Store manual bedtime's expiry as the next local 08:00 converted to an absolute timestamp, not “24 hours later.” Persist the override so a process restart or reboot does not clear bedtime. On startup discard expired overrides and recompute from the current time. systemd accepts IANA zones for calendar expressions. [systemd time syntax](https://github.com/systemd/systemd/blob/main/man/systemd.time.xml)
4. Keep an explicit `scheduled`, `bedtime`, or `awake override` state separate from the hardware's observed on/off state. The latest deliberate sleep/wake action must win under serialization. **Still to decide:** how long an explicit wake lasts and whether it wakes the lid LEDs too. A reasonable candidate is expiry at the next schedule boundary; this is a proposal, not an accepted user decision.

Locally checked calendar parsing across the 2026 spring/autumn DST transitions with `systemd-analyze calendar`: 08:00 Oslo resolves to 06:00 UTC in summer and 07:00 UTC in winter. This machine requires `TZDIR=/etc/zoneinfo` for that CLI check; the target runtime must have timezone data available too. This verifies calendar examples, not timer deployment or the target host clock.

## AniMe: normal off versus stronger darkness guarantees

Stopping the stats producer and sending `asusctl anime --enable-display false` covers its normal lifecycle. **It does not cover every event in pinned asusctl 6.3.7.** The version's `set_enable_display` persists the requested setting, but its lid-open and external-power handlers issue enable packets without checking `display_enabled`. Reload also sends an enable packet before subsequently applying disabled state in some conditions. These are source-level findings; visible light or flicker has not been observed. [Versioned AniMe implementation, especially `set_enable_display`, `create_tasks`, and `reload`](https://gitlab.com/asus-linux/asusctl/-/blob/6.3.7/asusd/src/aura_anime/trait_impls.rs)

The next design must select a defense: validate a policy-aware fix/newer daemon, or test a combined **brightness Off plus display disabled** strategy with dark startup defaults and policy-controlled restoration of daytime brightness. The latter is plausible because the version's brightness setter writes an Off brightness packet as well as disabling the display, whereas the lid-open handler only toggles enable; it is not a proven device guarantee. Do not require a patch solely on this investigation. Keep asusd's unrelated laptop controls available. [Brightness and event setters](https://gitlab.com/asus-linux/asusctl/-/blob/6.3.7/asusd/src/aura_anime/trait_impls.rs), [brightness packet encoding](https://gitlab.com/asus-linux/asusctl/-/blob/6.3.7/rog-anime/src/usb.rs)

## Boundaries and implementation acceptance

Hardware proof is **not required to choose a GUI or TUI architecture now**. It is required before declaring the implementation bedroom-safe. Verify panel/backlight darkness and recovery, AniMe darkness during AC/lid events and asusd restart, reboot during quiet hours, expired/persisted overrides, app/compositor crash recovery, random keyboard/mouse input, an incoming alert, and continued cluster availability throughout. Inspect the actual connector, GPU driver, backlight interfaces, exact model, and all remaining indicator/keyboard LEDs.

An operating-system controller cannot enforce policy before its driver and service exist. Firmware screens, bootloader output, early kernel console, and firmware LED behavior are separate limits; even a correctly reconciled session may briefly light during boot or compositor recovery. The final design must state whether it promises ordinary scheduled darkness or also requires eliminating these flashes, with model-specific investigation if the stronger guarantee matters. No live host was accessed and no physical power action was attempted. Cooling benefit from an open lid remains unverified.
