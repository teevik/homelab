# Laptop dashboard directly on a Linux virtual console

Research for [Verify virtual-console startup, shell handoff, and night control](https://github.com/teevik/homelab/issues/68), part of [Design a distinctive laptop health display](https://github.com/teevik/homelab/issues/62). Investigated 2026-09-30 against repository baseline `13103fe5a246dcd6e1d4444bbf4e5080182a3818`. Planning only: no host login, production changes, or physical display actions.

## Conclusion

A Rust/Ratatui dashboard can start directly on `tty1`, and an intentional Ctrl+C can leave the user at the same console's shell. A compositor and graphical terminal are unnecessary for that interaction. Keep the independent collector and display-policy controller. Replace compositor shortcuts with an existing system-level hotkey daemon, and replace Sway output control with verified console/backlight controls. The startup architecture is source-supported; actual panel darkness remains an implementation acceptance check, not a fact established by this research.

During this investigation the owner explicitly selected automatic login to the normal `teevik` account on `tty1`, with Ctrl+C returning to that account's shell and `dashboard` relaunching the UI. The current account has wheel membership and passwordless sudo; the owner accepted this existing privilege boundary. The UI should still read the normalized collector snapshot and must not automatically load an administrative kubeconfig, but it is no longer valid to claim the renderer is isolated from administrative credentials or privileges. [Current account configuration](https://github.com/teevik/homelab/blob/13103fe5a246dcd6e1d4444bbf4e5080182a3818/modules/nixos/standard.nix).

## Boot, foreground process, and shell handoff

The pinned getty module provides `services.getty.autologinUser`. Its default repeated-autologin arguments apply to the getty template, including more consoles than just `tty1`; do not assume that setting alone scopes autologin to one console. `autologinOnce = true` explicitly limits the automatic login to `tty1` once per boot, using a `/run` marker. Without autologin, normal authenticated login is available, but then the dashboard cannot appear unattended immediately after boot. Repeated autologin on only `tty1` needs an explicit per-instance configuration. [Pinned getty module](https://github.com/NixOS/nixpkgs/blob/e5bdc4a41d4c072fe1e3787eaa0320a384741d44/nixos/modules/services/ttys/getty.nix).

Recommended session shape:

```text
getty on tty1 → login shell → foreground dashboard launcher → Ratatui
                              deliberate exit returns ↗ to shell prompt
```

Use `teevik`'s actual interactive login-shell initialization, guarded by account identity, exact controlling terminal `/dev/tty1`, interactive state, and an inherited once-per-session marker. The repository does not explicitly override this account's shell in `standard.nix`; confirm the evaluated shell before selecting the hook. Exclude SSH sessions and nested shells. Launch a child and wait for it; do not `exec` it over the shell. NixOS exposes Bash login initialization separately from general interactive initialization. Scope any global NixOS hook explicitly rather than launching on every shell. These are design recommendations using the available initialization mechanism. [Pinned Bash module](https://github.com/NixOS/nixpkgs/blob/e5bdc4a41d4c072fe1e3787eaa0320a384741d44/nixos/modules/programs/bash/bash.nix).

Crossterm raw mode prevents the terminal driver from processing Ctrl+C normally. The application must recognize the Ctrl+C key event, exit its event loop intentionally, and restore terminal state. It should use a distinct successful/intentional result rather than leave the launcher to guess whether a failure was a quit. [Crossterm raw-mode documentation](https://docs.rs/crossterm/0.29.0/crossterm/terminal/index.html).

Restore raw mode, cursor visibility, screen state and changed attributes on normal exit, ordinary errors and panic. Ratatui supplies restoration helpers; the wrapper should also retain the pre-launch terminal settings and restore them after an uncatchable child termination. A killed process cannot run its own cleanup. Keep the wrapper attached to the foreground job and make Ctrl+C cancel its retry delay too. [Ratatui restoration API](https://docs.rs/ratatui/latest/ratatui/fn.restore.html), [Ratatui terminal lifecycle](https://ratatui.rs/concepts/backends/raw-mode/).

Preserving automatic crash recovery and intentional shell access requires a small launcher policy: successful intentional exit returns immediately; unexpected failure restores the terminal, retries with bounded backoff, then leaves a usable prompt after repeated failure. Do not wrap intentional exit in an unconditional restart loop or a `Restart=always` display service. The getty/session must remain alive while the shell is being used. Provide a simple `dashboard` command for deliberate relaunch. Collector/policy services recover independently; quitting the UI changes neither monitoring nor darkness policy. These are proposed implementation semantics, not behavior supplied automatically by autologin.

## Console appearance and compatibility

NixOS provides `console.font`, `console.packages`, `console.keyMap`, and a 16-entry `console.colors` palette. Choose a large PSF console font and map the amber/ivory design to named/indexed colors; do not assume arbitrary RGB output or graphical-terminal font fallback. The initial font must cover the actual symbols used. Prefer ASCII/simple line drawing and block charts over unverified emoji, Nerd Font icons or Braille. A larger font trades information density for distance readability, so retain the attention summary even when detailed service rows scroll. [Pinned console configuration](https://github.com/NixOS/nixpkgs/blob/e5bdc4a41d4c072fe1e3787eaa0320a384741d44/nixos/modules/config/console.nix).

Use the real `TERM=linux`; do not label the console `xterm-256color` to bypass capability checks. Upstream Linux 6.18 does implement the DEC 1049 alternate-screen operation, so old blanket claims that the Linux console cannot restore an alternate screen are not applicable to that baseline. Verify actual terminal entry/exit on the booted kernel and provide a clean prompt even if screen restoration is unavailable. [Linux 6.18 terminal parser, `csi_DEC_hl`](https://github.com/torvalds/linux/blob/v6.18/drivers/tty/vt/vt.c).

## Darkness is independent of the dashboard

The controller remains a host service, with one serialized policy for screen and AniMe, independent of the login shell, UI and collector. Preserve the accepted Europe/Oslo 23:00–08:00 schedule, persisted bedtime until the next local 08:00, ten-minute screen-only wake, same-boot wake recovery and reboot-cleared wake. Ctrl+C only exits the UI; it does not implicitly wake the panel, clear bedtime, or disable the controller.

`setterm --blank force` is an available console mechanism that keeps the screen blank despite keypresses; `--blank poke` explicitly unblanks. The utility warns that console operations may use stdin, so an independent service must address the actual console on both stdin and stdout (or issue the equivalent ioctl directly). Ordinary timed console blanking is insufficient for the no-wake-on-input policy. `--powersave`/`--powerdown` are separate controls and should not be assumed to work on the laptop merely because the options exist. [util-linux setterm manual](https://github.com/util-linux/util-linux/blob/master/term-utils/setterm.1.adoc).

In Linux 6.18, `TIOCL_BLANKSCREEN` sets `ignore_poke` before blanking; the normal poke path returns without unblanking while that flag is set. Ordinary buffered display updates are gated by console blank state. Explicit unblank clears the flag. This supports normal input/update suppression, not a universal no-flash guarantee against every driver or console transition. [Linux 6.18 `tioclinux`, `poke_blanked_console`, `con_should_update`, `do_unblank_screen`](https://github.com/torvalds/linux/blob/v6.18/drivers/tty/vt/vt.c).

Text-to-text VT switching does not take the explicit mode-change unblank path in `complete_change_console`; graphics-to-text transitions and `KDSETMODE` can call `do_unblank_screen` directly. Thus do not claim forced blanking survives arbitrary graphical programs or mode changes. Console-switch code also invokes the low-level display driver's switch operation, so exact graphics/driver behavior still needs testing. [Linux 6.18 VT ioctl and switching](https://github.com/torvalds/linux/blob/v6.18/drivers/tty/vt/vt_ioctl.c), [Linux 6.18 framebuffer console](https://github.com/torvalds/linux/blob/v6.18/drivers/video/fbdev/core/fbcon.c).

Use an independent, verified panel/backlight off control as the physical darkness defense. Linux's backlight ABI defines `bl_power=4` as off and `0` as on; brightness and actual brightness are separate attributes. Discover the real panel's device and preserve the intended daytime brightness rather than guessing a path or setting maximum brightness. Driver implementation determines what an attribute write actually achieves. A sysfs readback alone is not physical proof that the backlight is dark. [Kernel backlight ABI](https://www.kernel.org/doc/Documentation/ABI/stable/sysfs-class-backlight).

For framebuffer drivers using the DRM fb helper, `FB_BLANK_POWERDOWN` maps to DRM DPMS off and ordinary blanking to standby. This is evidence of a possible real power path, not proof that the actual host uses that helper or honors it for its panel. If needed, inspect the discovered framebuffer's supported blank/power interface during implementation. [Linux 6.18 DRM fb helper](https://github.com/torvalds/linux/blob/v6.18/drivers/gpu/drm/drm_fb_helper.c).

Reconcile at boot, schedule/manual events, controller/device recovery, VT changes and periodically. Keep the backlight off while changing console state; restore only for policy-approved wake/daytime. Monitoring VT events and reapplying darkness after a switch is useful recovery, but cannot establish that there was no intervening flash. If a driver reenables the light despite the independent off control, the implementation needs a stronger tested control/driver solution before acceptance. Do not quietly replace physical darkness with a black image or a polling promise.

## Deliberate keyboard actions after the UI exits

The pinned NixOS `services.triggerhappy` module offers systemwide key combinations, press/hold/release selection, a service/socket and udev hotplug handling. It provides a practical existing replacement for compositor shortcuts. Bind only the three fixed controller commands (bedtime, ten-minute wake, resume schedule), on press rather than autorepeat. It must remain available at the dashboard, shell and login prompt. Restrict its command permissions and avoid giving the display account access to all input devices. [Pinned triggerhappy module](https://github.com/NixOS/nixpkgs/blob/e5bdc4a41d4c072fe1e3787eaa0320a384741d44/nixos/modules/services/hardware/triggerhappy.nix).

Triggerhappy works without a graphical session or logged-in user. Its ordinary device opening does not exclusively grab the keyboard, preserving the console's input. Consequently the chosen chord can also reach the foreground program: choose deliberate nonconflicting combinations and verify their console/shell behavior, or reserve them in the console keymap during implementation. Do not commandeer the power button or Ctrl+C. The daemon can drop privileges after opening devices; dispatch fixed authorized requests to the policy controller. [Upstream manual](https://github.com/wertarbyte/triggerhappy/blob/master/thd.pod), [device opening](https://github.com/wertarbyte/triggerhappy/blob/master/thd.c).

A console keyboard request can activate systemd's `kbrequest.target`, but that gives one undifferentiated action and needs checking existing rescue-target wiring/keymap behavior. It is unnecessary when preserving all three accepted shortcuts with triggerhappy. Shell aliases are useful conveniences but cannot act as global hotkeys while another process owns input. SSH invokes the same three controller commands. [systemd special targets](https://github.com/systemd/systemd/blob/main/man/systemd.special.xml).

## Implementation acceptance and remaining decisions

1. Boot autologs into the owner-selected `teevik` account on `tty1` and starts the dashboard there. SSH, nested shells and other VTs do not autostart it or acquire autologin. Keep the owner-accepted existing account privileges explicit. Configure and document whether a full shell logout returns to autologin or authentication; this does not change Ctrl+C returning to the still-running shell.
2. Ctrl+C leaves an immediately usable shell, with echo, canonical input, cursor and attributes restored. The dashboard stays stopped while shell commands run. Manual `dashboard` relaunch works. Crash/panic/forced-kill and repeated-failure paths recover or yield a usable prompt as specified.
3. Verify actual console font/glyphs/colors and main status readability at approximately one metre; measure the collector, UI and small helper services without assuming savings in advance.
4. At night, exercise ordinary keys, Ctrl+C, shell command output, continued UI updates, mouse input and all text VTs. None may illuminate the screen. Test explicit global shortcuts with UI running, UI exited and at the login prompt; test SSH too. Check chord leakage does not accidentally edit/submit shell input.
5. Physically verify backlight darkness and ten-minute screen-only wake, including expiry while a shell is in use, VT changes, controller/hotkey daemon restart and relevant device/lid/AC events. Record the actual device and control used; failed control must fail acceptance, not become a black-screen substitute.
6. Preserve existing schedule, DST, bedtime persistence and reboot tests; UI quit cannot suspend the host or stop collection. Retain permitted firmware/early-boot flashes and the earlier AniMe acceptance requirements.

There is no new documentary prerequisite to choosing direct TTY rendering. The owner has answered the account choice. Panel discovery, raw-console rendering, exact login lifecycle configuration and no-flash physical checks are implementation acceptance work. If those checks show the chosen hardware cannot maintain darkness, reopen that specific mechanism before declaring implementation complete.
